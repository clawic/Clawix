# ADR 0029: Accessibility governance

Status: accepted

## Context

Constitution IX.8 makes accessibility non-optional for every Clawix surface,
including UI generated by agents. `STANDARDS.md` defines baseline rules for
assistive technology, keyboard operation, traversal order, contrast, and target
sizes. Interface governance under `docs/ui/` protects visual canon, but it does
not by itself provide an equivalent operational program for screen reader
behavior, keyboard navigation, focus order, reduce-motion behavior, text
scaling, timed interactions, semantic labels, or generated UI.

Accessibility is related to visual UI, but it is not the same authority lane.
Some accessibility work is functional wiring, while other work changes visible
copy, layout, motion, or contrast and must still obey the visual/copy/layout
mutation boundary.

## Decision

Clawix accessibility work is governed by a cross-platform Accessibility
Governance Program under `docs/accessibility/`.

The program applies to macOS, iOS, Android, and Web from day one. Its required
axes are screen reader semantics, keyboard navigation, focus order, visible
focus, contrast, reduced motion, text scaling, alt or semantic labels, time
alternatives, and agent-generated UI. Every governed visible surface must map to
those axes or carry an explicit expiring gap.

The public repo stores only safe governance metadata: manifests, check names,
surface ids, evidence aliases, hashes, and external-pending labels. Real screen
reader transcripts, signed-host captures, private screenshots, local paths,
device evidence, and human approval artifacts stay private or external.

Accessibility governance does not grant visual authority. If an accessibility
fix changes presentation or user-visible copy, it must also pass the existing
interface governance lane in `docs/adr/0010-interface-governance.md` and
`docs/ui/`.

Agent-generated UI inherits the same baseline. Generated/custom UI must declare
an accessibility contract before it can be treated as complete: semantic names,
keyboard reachability, focus handoff, reduced-motion behavior, text scaling,
contrast, timed-interaction alternatives, and validation evidence.

## Surface Parity

- **Human surface**: `docs/accessibility/README.md`, `STANDARDS.md`, and UI
  implementation evidence tell humans which accessibility contract applies.
- **Programmatic surface**: `scripts/accessibility_governance_guard.mjs`
  validates manifests, required axes, generated-UI rules, surface coverage, and
  expiring gaps.
- **Persistence**: `docs/accessibility/*.manifest.json`,
  `docs/accessibility/completion-audit.md`,
  `docs/discoverability.registry.json`, and
  `docs/adr-operational-coverage.manifest.json`.
- **Validation**: `node scripts/accessibility_governance_guard.mjs`,
  `node scripts/accessibility_governance_guard.mjs --self-test`,
  `node scripts/constitution-assertions-check.mjs`,
  `node scripts/discoverability-check.mjs`, and `bash scripts/test.sh fast`.

## Performance Impact

The governance layer is static JSON, Markdown, and a Node.js guard in the fast
lane. Runtime accessibility work can affect focus handoff, animation choices,
text layout, and bridge-backed UI responsiveness, so implementation tasks must
continue to classify performance-sensitive behavior through existing UI and
performance governance when they change live surfaces.

## Decision Tensions

- **Prioritized axes**: any-human access, constitutional IX.8 coverage,
  generated-UI parity, deterministic validation, and private evidence safety.
- **Constrained axes**: accessibility governance must not become a back door
  for unauthorized visual, copy, layout, or motion changes.
- **Tradeoffs accepted**: some proof remains EXTERNAL PENDING because screen
  reader transcripts, signed-host evidence, device evidence, and human approval
  are not safe public artifacts.
- **Debt or pending evidence**: current coverage starts as public governance
  plus evidence aliases; real assistive-tech and device runs are ledgered in the
  completion audit until approved evidence exists.
